# 联网检查更新 — 设计文档

- 日期：2026-09-28
- 状态：待评审
- 目标版本：3.2.11（未定，版本号由用户决定）
- 相关 issue：#10（应用内更新日志的后续演进）

## 1. 背景

当前应用**完全没有联网能力**：无 `INTERNET` 权限、无任何 HTTP 依赖。更新日志靠
`Changelog.kt` 内置（发版时手工同步），用户只能看到自己这一版改了什么，
**无法得知是否有新版本**。

这带来一个具体缺失：`CHANGELOG.md` 顶部长期挂着

> 3.2.8 及更早版本存在恶性缺陷：连接耳机后可能让耳机死机 / 自动关机 / 断开

但这条警告**只有用户主动去翻才看得到**。旧版用户不会收到任何提醒。

本设计引入联网检查更新，并把「在线更新日志」作为内置内容的补充。

## 2. 范围

**做：**

- 检查是否有新版本（正式版 / 预发布双通道）
- 展示最新版的更新日志（在线优先，内置兜底）
- 点「更新」直接跳转到 APK 下载链接
- 设置项：联网总开关 + 更新通道
- 引导页新增一页，首次使用时询问是否开启联网

**不做（YAGNI）：**

- **应用内下载 APK** / 断点续传 / 静默安装 — 即把文件下到本机再由应用发起安装。
  本设计只做「跳浏览器下载」（§6.3），不做应用内下载：模块需在 LSPosed 里安装并重启作用域，应用内安装体验更差，还要引入存储权限
- 后台定期检查、通知栏推送 — 边际收益小，却要引入后台网络唤醒
- 自定义更新源 / 镜像源切换
- GitHub token 认证（见 §4.2）
- 遥测、统计、任何形式的数据上报

## 3. 关键实测结论

以下均为本机实测，非推断。它们直接决定了架构选型。

| # | 结论 | 证据 |
|---|---|---|
| 1 | 未认证 GitHub API 限流 **60 次/小时/IP**，且已实测撞到 | `curl /rate_limit` → `remaining=0`；`releases/latest` → **HTTP 403** |
| 2 | `github.com/<repo>/releases.atom` **不占 API 配额** | API 403 期间该地址仍 **HTTP 200**，返回 10 条 release |
| 3 | `raw.githubusercontent.com` **不占 API 配额** | 同期 **HTTP 200**，CHANGELOG.md 114KB |
| 4 | **atom 只列 10 条，且会被 CI 预发布挤出** | 实测正式版 `330-3.2.10` 已被挤到**第 6 位**，前 5 全是 `ci-N` |
| 5 | APK 下载链接可直接构造，不占配额 | `releases/download/<tag>/app-release.apk` → **HTTP 302** → CDN（正式版与 `ci-N` 同一模式） |
| 6 | APK 内含构建 commit，可用于精确比对 | `META-INF/version-control-info.textproto` → `revision: "200cfe4..."` |
| 7 | `ci-N` 的 release body 含完整 commit sha | body 内 `提交：<code>a1750e0dc938...</code>` |

**结论 2/3 合起来给出一个不限流的兜底通道；结论 4 说明兜底不能单独用**——
这正是「API 为主、atom 兜底」的原因。

## 4. 关键设计决策

### 4.1 双通道语义

| 通道 | 取哪个 release | 版本比对依据 |
|---|---|---|
| 正式版（默认） | `releases/latest`（该端点只返回非预发布，天然跳过 `ci-N`） | tag `330-3.2.10` → 解析出版本号 330，与已装 versionCode 比较 |
| 预发布 | 最新一条 release（含 `ci-N`） | `ci-N` **不含版本号**，改用 commit 比对（结论 6/7） |

预发布通道的比对：从 `ci-N` 的 body 里提取 commit sha，与 APK 内
`version-control-info.textproto` 的 revision 比对。相同 = 已是最新。

> **已知局限**：本地增量构建时 Gradle 可能跳过
> `extractReleaseVersionControlInfo`（up-to-date），导致该文件滞后一次提交。
> CI 全新构建则准确。因此本地构建可能误报「有新版本」。
> 这是本地开发场景的已知误差，不影响发布产物；文档如实记录，不额外兜底。

`ci-N` 的 body 是 CI 模板（只有 commit），**不能当更新日志展示**。
预发布通道下只显示版本标识，并提供「查看本次变更」链接指向
`https://github.com/bqj6666/FxxkMoondrop/commit/<sha>`。

### 4.2 认证：不做

- 未认证 60 次/小时/IP，加缓存后每用户每天 1~2 次，**完全够用**
- 把 token 打进 APK 会被 `strings` 轻易提取，且 GitHub 会自动吊销出现在公开仓库的 token
  —— 纯风险、零收益
- 读的是公开仓库，这些端点本来就不要求认证

国内运营商大量使用 CGNAT，多用户共享出口 IP，60/小时 存在被邻居耗尽的可能。
这就是 §3 结论 2 那条兜底通道的价值。

### 4.3 更新日志来源：release body，不解析 CHANGELOG.md

一次请求同时拿到版本号与更新日志。且 `tools/release_notes.py` 已把 CHANGELOG
渲染成 release body，**连置顶的恶性缺陷警示都带**——那正是想给用户看的最终形态。

`Changelog.kt` **保留不删**：离线、被限流、开关关闭时仍要靠它。
在线内容拿不到就回落，用户永远有东西可看。

### 4.4 零新增依赖

用系统自带的 `HttpURLConnection` + `org.json`。不引 OkHttp/Retrofit
—— 为一次 GET 请求引入依赖不划算。

## 5. 组件设计

### 5.1 新增 `UpdateChecker.kt`（唯一新增文件）

联网逻辑全部收口于此，便于独立测试与审计。

```
object UpdateChecker {
    enum class Channel { STABLE, PRERELEASE }

    data class UpdateInfo(
        val tag: String,          // "330-3.2.10" 或 "ci-199"
        val versionName: String?, // 正式版才有；预发布为 null
        val versionCode: Int?,    // 正式版才有
        val commitSha: String?,   // 预发布才有
        val notes: String?,       // 更新日志（正式版）；预发布为 null
        val downloadUrl: String,  // 直接构造，不请求
    )

    /** 读缓存的检查结果；超过 TTL 或 force 才真正联网。绝不在主线程调用。 */
    @JvmStatic fun check(ctx: Context, force: Boolean): Result
}
```

**职责边界**：这个对象只负责「拿到远端最新版信息并与本地比较」，
不碰 UI、不写 SP 开关、不发通知。UI 侧只消费它的返回结果。

### 5.2 数据源与降级顺序

```
1. api.github.com/repos/<repo>/releases[/latest]   ← 主路径，精准
        ↓ 403 / 超时 / 解析失败
2. github.com/<repo>/releases.atom                 ← 兜底，不占配额
        ↓ 同样失败
3. null → UI 回落内置 Changelog.kt，不显示「有新版本」
```

超时：连接 5s、读取 8s。整个检查必须离开主线程。

### 5.3 缓存

- 存 SharedPreferences：最后检查时间、结果快照、通道
- TTL **6 小时**；`force=true`（手动按钮）绕过
- 进「关于」页触发检查时走缓存，不重复打网络

### 5.4 存储

新增 SP 键（沿用既有 `cfg` 表，与设置页同源）：

| 键 | 默认 | 说明 |
|---|---|---|
| `net_update_check` | **`false`** | 联网检查总开关（默认关，见 §9.1） |
| `update_channel` | `0` | 0 = 正式版，1 = 预发布 |

## 6. UI 设计

### 6.1 设置 → 功能

新增一组「更新」，两项：

- **联网检查更新**（开关，默认关）— 副标题说明会访问 GitHub 且不收集任何数据
- **更新通道**（下拉：正式版 / 预发布）— 仅开关打开时可见

### 6.2 引导页：新增独立一页

- 位置：`pageInjection()`（系统集成）之后
- 需同步改：`PAGE_COUNT` 7 → 8、新增页码常量、`buildPages()` 插入
- 内容：联网开关（**默认关**）+ 通道选择（默认正式版）+ 隐私说明
  （「只访问 GitHub 公开接口，不发送设备信息，不收集任何数据」）
- 与设置页**共用同一份 SP**，两处必须双向同步

### 6.3 关于页 → 更新日志弹窗

行为改为**在线优先、内置兜底**：

| 状态 | 显示 |
|---|---|
| 开关关 | 现有内置内容，不显示更新提示，不发任何请求 |
| 检查中 | 内置内容 + 顶部「正在检查更新…」 |
| 有新版 | 顶部条「发现新版本 3.2.11」+ **「下载」按钮 → 直接打开下载链接** |
| 已最新 | 「已是最新版本（3.2.10）」 |
| 检查失败 | 静默回落内置内容，不报错、不打扰 |

- 进页面自动查一次（走缓存）
- 新增「检查更新」行 → `force=true`
- 预发布通道：日志区显示「最新预发布构建 ci-199」+
  「查看本次变更」→ commit 链接
- 点「下载」用 `ACTION_VIEW` 打开 §3 结论 5 的 URL，交给系统浏览器

## 7. 错误处理

**联网失败绝不影响任何现有功能** —— 这是硬要求：

- 所有网络异常（超时、403、证书、DNS、解析）一律吞掉，`check()` 返回结果对象
- 不弹 toast、不写错误通知、不阻塞 UI
- 开关关闭时**不创建任何连接**（不是「连了不显示」）

## 8. 隐私

- 只对 `api.github.com` / `github.com` / `raw.githubusercontent.com` 发起 GET
- **不发送任何设备信息、不传查询参数、不带 token、无 cookie**
- 无第三方依赖，无埋点
- 清单只新增 `INTERNET` 一个权限

## 9. 已知取舍

### 9.1 默认关闭的代价（已确认接受）

联网**默认关**，意味着 §1 那个恶性缺陷警告**只有主动开启的用户才能收到**，
默认安装的旧版用户仍然不会知道。这与「让用户知道自己该更新」的初衷相抵。

该取舍由用户明确定下（2026-09-28），此处如实记录。若日后希望提高触达，
最小改动是把默认值改为 `true` 并在引导页显著说明。

### 9.2 预发布通道的比对精度

见 §4.1 的已知局限（本地增量构建的 commit 可能滞后一次）。

### 9.3 限流

单 IP 60 次/小时。已有 6 小时缓存 + atom 兜底，预期不会触达。
若真被限流，表现为「检查失败」，静默回落，无用户可见故障。

## 10. 测试计划

实现后必须实测以下各项，逐条取证：

1. 正式版通道：正确识别「已是最新」与「有新版本」
2. 预发布通道：识别 `ci-N`，commit 比对生效，显示 commit 链接
3. **开关关闭时零网络请求**（logcat / 抓包确认，不是「连了不显示」）
4. 断网、超时、403 三种失败各自回落内置日志，不崩不卡
5. 缓存生效：6 小时内重复进页面只打一次网络
6. 下载链接在系统浏览器里**真的开始下载**
7. 引导页与设置页开关**双向同步**（同一 SP）
8. 单测覆盖：tag 解析（`330-3.2.10` / `ci-199`）、版本比较、commit 提取
9. 引导页页码改动不破坏既有流程（7 → 8 页）
